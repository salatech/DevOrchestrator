# DevOrchestrator MVP — Architecture & Implementation Plan

## Objective

Build the complete first-milestone flow:

```
devai init → devai plan "..." → Human approval → devai execute PLAN-001
→ Coding agent → Workspace changes → Tests → Diff → Final report
```

Plus the essential supporting commands: `devai status`, `devai context`, `devai plans`, `devai show`, `devai approve`, `devai review`, `devai run`, `devai diff`, `devai doctor`.

---

## Technology Decisions

Based on 2026 ecosystem research, the MVP will use:

| Component | Choice | Rationale |
|-----------|--------|-----------|
| CLI framework | **Citty** (`unjs/citty`) | Zero-dep, lazy subcommands, best TS type inference |
| Interactive prompts | **@clack/prompts** | Modern UX (used by Vite, Astro, Nuxt) |
| Colors | **picocolors** | 14x faster than chalk, zero-dep, no supply-chain risk |
| Spinners | **Clack's built-in `spinner()`** | Visual consistency with prompts |
| Testing | **Vitest** | ESM-native, zero-config TS, instant startup |
| Frontmatter parsing | **`yaml`** package + custom parser | No abandoned deps, full control, strict typing |
| Git integration | **`simple-git`** | Full CLI git wrapping, inherits user config |
| Build tool | **tsup** | esbuild-based, sub-50ms startup, shebang injection |
| Dev runner | **tsx** | Run TS directly during development |
| LLM abstraction | **Vercel AI SDK v7** (`ai`) | Industry-standard multi-provider abstraction |
| Provider adapters | **@ai-sdk/openai**, **@ai-sdk/anthropic** | Standardized streaming + tool calling |
| Schema validation | **Zod** | Structured outputs, tool definitions, config validation |
| CLI agent spawning | **execa** | Process management for Codex/Claude Code |
| Markdown tables | **cli-table3** | For `devai status` output |

### Key Decision: Vercel AI SDK as Engine (Wrapped)

The updated research strongly recommends using `ai` (Vercel AI SDK v7) as the underlying multi-provider engine, but wrapped in our own thin `ModelOrchestrator` layer. This gives us:

- Normalized streaming across all providers
- Built-in tool calling loops (`maxSteps`)
- Zod-based structured outputs
- Provider-agnostic code in the core

We do NOT leak Vercel AI SDK types into the core orchestrator. Our internal interfaces wrap it.

### Key Decision: Citty over Commander.js

Citty provides:
- Zero runtime dependencies (uses Node's native `util.parseArgs`)
- Lazy/async subcommand loading (critical for CLI startup performance)
- Superior TypeScript type inference from argument definitions
- Used by the UnJS ecosystem (Nuxt, Nitro, Vite tooling)

### Key Decision: CLI Agent Spawning

For MVP, coding agents (Codex, Claude Code) are invoked as CLI subprocesses via `execa`, not via API. This is the most practical approach because:
- Codex CLI supports `codex exec --json` for headless execution
- Claude Code has `@anthropic-ai/claude-agent-sdk` for programmatic access
- This avoids building a full agent runtime for MVP

#### Step 4.3 — Plan state machine

Explicit valid transitions:

```
draft → awaiting_approval
awaiting_approval → approved | cancelled
approved → executing | cancelled
executing → validating | failed

reviewing → completed | failed | executing (fix)

```

Invalid transitions throw `PlanningError`.

- `listPlans()` → lists all plans with status
- `getNextId()` → auto-increment (`PLAN-001`, `PLAN-002`, ...)
- `transitionStatus(id, newStatus)` → validates transition + updates

#### Step 5.2 — Context collector

Gathers raw context from all sources:
- Read `.ai/PROJECT.md`, `ARCHITECTURE.md`, `CONVENTIONS.md`
- Read applicable `.ai/skills/*/SKILL.md`
- Read `package.json` / `pyproject.toml` / etc.
- Get git state
- List existing plans

#### Step 5.3 — Context selector (heuristic-based)

Given a natural-language request, select relevant source files:

1. **Keyword extraction** — extract nouns, technical terms from request
2. **File path matching** — match keywords against file paths
3. **Import graph** — if a matched file imports others, include them
4. **Test association** — if `foo.ts` is matched, include `foo.test.ts`
5. **Recently modified** — include recently changed files (higher relevance)
6. **Configured relevance** — if `.ai/` context mentions specific files, boost them

Limit total context to `config.limits.maxContextFiles`.

#### Step 5.4 — Context engine facade

```typescript
class ContextEngine {
  async buildContext(request: string, workspace: WorkspaceManager): Promise<TaskContext> {
    const collected = await this.collector.gather(workspace);
    const relevant = await this.selector.select(request, collected);
    return this.assemble(collected, relevant);
  }
}
```

### Phase 7: Security Layer

#### Step 7.1 — Command policy

```typescript
type CommandPolicy = 'safe' | 'requires_approval' | 'blocked';

class CommandPolicyChecker {
  getPolicy(command: string): CommandPolicy;
}
```

Default policies:

| Pattern | Policy |
|---------|--------|
| `npm test`, `npm run test`, `pnpm test` | safe |
| `npm run lint`, `pnpm lint` | safe |
| `tsc --noEmit`, `npx tsc` | safe |
| `npm run build`, `pnpm build` | safe |
| `git status`, `git diff`, `git log` | safe |
| `npm install *`, `pnpm add *` | requires_approval |
| `git commit *`, `git push *` | requires_approval |
| `rm -rf *`, `rm -r *` | blocked |
| `DROP TABLE`, `DELETE FROM` | blocked |

#### Step 7.2 — Command executor

```typescript
class CommandExecutor {
  async execute(command: string, options?: ExecOptions): Promise<CommandResult> {
    const policy = this.policyChecker.getPolicy(command);
    if (policy === 'blocked') throw new SecurityError(...);
    if (policy === 'requires_approval') {
      const approved = await this.requestApproval(command);
      if (!approved) throw new SecurityError(...);
    }
    return this.run(command, options);
  }
}
```

#### Step 10.2 — Execution loop

```
1. Load approved plan
2. Snapshot workspace state (before)
3. Build execution context
4. iteration = 0
5. LOOP:
   a. Send task to executor
   b. Capture result
   c. If executor reports BLOCKED → abort, return block reason
   d. Run validation commands (lint, typecheck, test)
   e. If validation passes:
      f. Run reviewer
      g. If reviewer approves → COMPLETE
      h. If reviewer requests changes:
         i. iteration++
         j. If iteration >= maxIterations → FAIL (max iterations)
         k. Feed review findings to executor
         l. GOTO 5.a
   e2. If validation fails:
      f. iteration++
      g. If iteration >= maxIterations → FAIL (max iterations)
      h. Feed validation errors to executor
      i. GOTO 5.a
6. Snapshot workspace state (after)
7. Produce execution trace
8. Return execution report
```

#### Step 10.3 — Validation runner

```typescript
class ValidationRunner {
  async run(commands: string[]): Promise<ValidationResult> {
    const results = [];
    for (const cmd of commands) {
      const result = await this.commandExecutor.execute(cmd);
      results.push({ command: cmd, passed: result.exitCode === 0, output: result.output });
    }
    return { allPassed: results.every(r => r.passed), results };
  }
}
```
